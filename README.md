# json-examples-validator

Validates the `*.json-examples.json` files of a JSON Schema library against its schemas with **ajv + ajv-formats**, as a
CLI or as **vitest** tests. Example files follow [json-examples-schema](../json-examples-schema); the library layout follows
`json-schema-lib.ARCHITECTURE.yaml`:

```
schema/<major>.<minor>.<patch>/<name>.schema.json      (may be in subdirectories such as ide/)
schema/<version>/format-assert-fast|full/...            (generated by format-assert-generator)
examples/<major>/<minor>/<SubexT>[_defs-<DeF>].json-examples.json
```

`examples/0/1/foo_defs-bar.json-examples.json` validates against `$defs/bar` of `foo.schema.json` in the highest `schema/0.1.*`
(`--all-patches`: every patch, `--version 0.1.0`: exactly that one). The validation target is decided by the file name only
(root, or `$defs/<DeF>`); `groupPointer`, `name` and `pointer` are classification / highlighting and never change the result
(`pointer` is shown in failure messages).

## Use

```bash
npx json-examples-validator . --verbose
```

vitest (top-level `await`, one test per example and profile):

```ts
// examples.test.ts
import { defineExamplesTests } from 'json-examples-validator/vitest';
await defineExamplesTests({ root: new URL('.', import.meta.url).pathname });
```

Without a test framework: `runExamples(options)` returns `{ passed, failed, skipped, problems, ok }`.

## Profiles

Every example runs once per profile:

| profile | schema | `format` | expected result |
|---|---|---|---|
| `annotation` | original | ignored | `valid` |
| `assertion` | original | asserted by ajv-formats (`--formats-mode`, default full) | full: `valid@when_formatAssertionFull ?? valid@when_formatAssertion ?? valid`; fast: `valid@when_formatAssertion ?? valid` |
| `format-assert-full` | `format-assert-full/` copy | no `format` left; `pattern` instead | `valid@when_formatAssertionFull ?? valid@when_formatAssertion ?? valid` |
| `format-assert-fast` | `format-assert-fast/` copy | same | `valid@when_formatAssertion ?? valid` |

A profile whose directory does not exist is reported as skipped. Known differences (e.g. fast mode only checks the *shape*
of a date) are declared, never silent: `skip: [{ profile: 'format-assert-fast', file: 'foo', index: 3, reason: '...' }]`
in the options or in `<root>/json-examples-validator.config.json`.

## Error expectations

`expectedErrors` are checked when the expected result is *invalid*. The list is chosen with the same priority as `valid`:
`expectedErrors@when_formatAssertionFull` > `expectedErrors@when_formatAssertion` > `expectedErrors` (the scenario keys may only be
written for examples whose `valid@when_…` is `false`). Each expected error must be matched by a distinct ajv error
(`errorMatch: "exact"` on the example, or the `exactErrors` option, also requires equal counts):

- `instanceLocation` = ajv `instancePath`; `keyword` = ajv `keyword` (a list means "any of these", e.g. `["format", "pattern"]`)
- `params`: partial match against ajv's `params` (`{ "missingProperty": "id" }` tells *which* `required` failed)
- `schemaLocation`: JSON Pointer to the failing keyword; compared as a suffix either way (ajv reports paths relative to the referenced subschema)
- `message`: a string must be contained; `{ regex, keyword }` must all match / be contained. Wording is engine specific, so it is only
  compared when the file has no `engine` or declares `ajv`
- in the `format-assert-*` profiles only `instanceLocation` and `keyword` are compared (`pattern` replaced `format`, so paths, params and messages differ by construction)

An invalid scenario without any `expectedErrors` is reported as a warning (`requireExpectedErrors: 'off' | 'warn' | 'error'`).

## Reports and consistency checks

```bash
npx json-examples-validator . --report          # examples that are format-sensitive or declare the wrong valid* keys, with the keys to write
npx json-examples-validator . --check-wrappers  # also validate examples against examples/<M>/<m>/schema/*.json-examples.schema.json
```

`--report` runs every example under annotation, assertion (fast / full) and the generated copies, and prints e.g.
`suggested: "valid": true, "valid@when_formatAssertionFull": false`. Exit code 1 when a declaration is wrong or a generated copy
disagrees with the assertion it replaces. `--check-wrappers` verifies that the editor-facing wrapper schemas (`_hook_valid`) and this
tool agree (formats are not asserted there: a wrapper only knows `valid`).

## Remote references

Schemas may `$ref` other repositories. Remote references are fetched (transitively) unless mapped to local files:

```json
{ "refMap": { "https://raw.githubusercontent.com/me/other-repo/refs/heads/main/": "../other-repo" }, "offline": true }
```

(in `json-examples-validator.config.json`, or `--ref-map url=path` / `--offline`). A key ending in `/` maps a whole remote directory.
A document that declares another `$id` than the URL it was fetched from (renamed repository) is also registered under that URL.

## Notes

- Dot-directories below `schema/<version>` are skipped unless `includeDotDirs` / `--include-dot-dirs` / `--include-dot-dir .name` says otherwise (same rule as format-assert-generator, shared through `jsonschema-lib-layout`).
- All `*.schema.json` of a version are loaded into one ajv instance, so `$ref`s between files resolve by `$id`. `$schema` picks
  ajv 2020-12 (default), 2019-09 or draft-07. A library that declares its own meta-schema in `$schema` is used as it is (its schemas are not validated against that meta-schema). Default ajv options: `{ allErrors: true, strict: false }` (`ajvOptions` to change).
- Setup problems (no matching schema, malformed example file, ...) fail the run instead of being ignored.
- Example files are checked structurally (`jsons[]`, `group`, `valid`, `instance`, the `valid@…`/`expectedErrors@…` types); `--check-wrappers` additionally validates them against json-examples-schema.
